Experiment 1

1. Singleton Creational
File: js/core.js

Paanch classes Singleton hain kyunki inka ek se zyada object hona galat hoga:

  • BankConfig — bank ka naam, IFSC aur approval limits
  • DatabaseConnection — ek hi database connection
  • SessionManager — kaun login hai
  • CommandInvoker — command history
  • BankingFacade — system ka single entry point

Live proof: History page ke neeche getInstance() === getInstance() ka result dikhta hai.

2. Chain of Responsibility Behavioural
File: js/approval.js

Har paisa nikalne wali request is chain se guzarti hai: Account Status → Fraud Check → Clerk (10K) → Manager (1L) → Branch Head (10L) → Rejected. Jo handler sambhal sakta hai wahi approve karta hai, warna aage bhej deta hai.

Baad me humne chain me Account Status naam ka naya handler joda — aur kisi bhi purani class ko haath nahi lagana pada. Yahi is pattern ka asli fayda hai.

Live proof: Withdraw ya Transfer karo — result me poora approval trail dikhta hai ki kis handler ne kya kiya.

Experiment 2

3. Factory Method Creational
File: js/accounts.js

AccountFactory.openAccount() me sab common kaam hai, lekin asli object createAccount() banata hai jise har subclass override karti hai — SavingsAccountFactory, CurrentAccountFactory, FDAccountFactory. Har account type ke rules apne aap lag jaate hain.

Live proof: My Accounts par naya account kholo — type badalte hi rules ka box badal jaata hai.

4. Proxy Structural
File: js/accounts.js

Website kabhi bhi RealAccountService ko seedha use nahi karti. Beech me AccountProxy hai jo teen kaam karta hai:

  • Protection proxy — logged-in user hi account ka owner hai ya nahi
  • Virtual proxy — real object sirf zaroorat padne par banta hai
  • Logging proxy — har access access_log table me jaata hai

Live proof: History page par "Account Access Log" table dekho. Admin console par poore bank ka access log dikhta hai jisme DENIED entries bhi hoti hain.

Experiment 3

5. Abstract Factory Creational
File: js/channels.js

SmartBank teen channel par chalta hai. Har channel ke liye ek poori family chahiye: Theme + Layout + Wording. ATMFactory, MobileAppFactory aur WebPortalFactory teeno cheezein ek saath deti hain, isliye galat family kabhi mix nahi hoti.

Live proof: Header ke dropdown se channel badlo — colours, corners, font aur button ka text sab ek saath badal jaate hain.

6. Bridge Structural
File: js/payments.js

Payment ka kaam (Transfer / Bill / Recharge) aur payment ka raasta (UPI / Card / Net Banking / Wallet) do alag hierarchy hain. Abstraction ke andar gateway ka reference rakha hai — wahi bridge hai.

Live proof: Transfer aur Bills & Recharge par gateway badal kar dekho — fee aur processing steps gateway ke hisaab se badalte hain.

Experiment 4

7. Observer + Database Behavioural
File: js/observer.js (database layer js/core.js)

Balance badalte hi TransactionSubject apne saare observers ko update() bhejta hai. Paanch observers hain:

  • SMSObserver — mobile par SMS
  • EmailObserver — email alert
  • AppPushObserver — app notification
  • LowBalanceObserver — sirf tab bolta hai jab balance minimum se neeche jaaye
  • DatabaseLoggerObserver — transaction ko DB me save karta hai

Live proof: Settings se koi alert band karo, phir transaction karo — Notifications me wo message aayega hi nahi, baaki sab aayenge.

Database Connectivity
File: js/core.js → class DatabaseConnection

Browser se MySQL/Oracle seedha connect nahi hota, isliye browser ka localStorage database ki tarah use kiya hai. Uske upar SQL jaisa layer banaya hai — connect(), insert(), select(), update(), truncate().

Extra Patterns

8. State Behavioural
File: js/state.js

Account teen halat me ho sakta hai. Har halat ki apni class hai jo khud batati hai kya allowed hai: ActiveState (sab kuch), FrozenState (paisa aa sakta hai, ja nahi sakta), ClosedState (kuch bhi nahi). Isse code me if (status == "frozen") jaisi lines har jagah nahi likhni padti.

Live proof: Staff login se Bank Console me kisi account ko Freeze karo, phir us customer se withdraw karke dekho — approval chain ka pehla hi handler rok dega. Deposit phir bhi chalega.

9. Strategy Behavioural
File: js/strategy.js

Interest ka formula account class ke andar nahi hai. Har scheme ki apni class hai: SimpleInterestStrategy (Savings 4%), CompoundInterestStrategy (FD 7.5%, har 3 mahine), NoInterestStrategy (Current). Naya scheme aane par sirf ek nayi class banegi, purani ek bhi nahi badlegi.

Live proof: My Accounts par Interest Calculator dekho — account badalte hi formula aur numbers dono badal jaate hain. "Interest jama karo" dabao to wo asli me credit ho jaata hai.

10. Command Behavioural
File: js/command.js

Har transaction ek TransactionCommand object hai jisme execute() ke saath undo() bhi hai. CommandInvoker history rakhta hai (database ke command_log table me), isliye page badalne par bhi undo kaam karta hai.

Live proof: Deposit / Withdraw page ke neeche "Undo Last Transaction". Staff Bank Console se kisi bhi purani transaction ko Reverse kar sakta hai — balance wapas theek hota hai, original row par REVERSED lagta hai, aur customer ko alert chala jaata hai.

11. Decorator Structural
File: js/decorator.js

Account par extra services chadhayi ja sakti hain — Cashback, Overdraft, Insurance, Reward Points. Har feature ek wrapper class hai jo account ke upar chadh jaata hai. Har combination ke liye nayi class banane ki zaroorat nahi.

Ye features sach me kaam karte hain: Cashback bill/recharge par 1% wapas deta hai, Overdraft balance khatam hone par bhi Rs. 10,000 tak nikalne deta hai (approval chain usko dekhta hai), aur Reward Points har kharch par jamte hain.

Live proof: My Accounts par features tick karke save karo, phir bill pay karke dekho — cashback wapas aa jaayega.

12. Adapter Structural
File: js/adapter.js

"QuickPay" ek third party wallet service hai jiska code hum badal nahi sakte. Uska interface bilkul alag hai — wo paise me amount leta hai, method ke naam alag hain (walletTransfer, fetchCommission), aur result me statusCode deta hai.

WalletGatewayAdapter beech me khada hokar use humare PaymentGateway jaisa bana deta hai. Isliye QuickPay bhi Bridge pattern me waise hi lagta hai jaise UPI ya Card — baaki code ko pata bhi nahi chalta ki ye bahar wali service hai.

Live proof: Transfer par gateway me "QuickPay Wallet" chuno — result me adapter ke conversion steps dikhte hain.

13. Facade Structural
File: js/facade.js

System me ab bahut hisse hain — proxy, approval chain, gateways, observers, commands, state, decorators. Har page ko in sabse alag alag baat karni pade to code ganda ho jaayega. BankingFacade ek simple darwaza hai: transact(), undoLast(), setStatus(), applyInterest(), statement().

Live proof: Kisi bhi page ka <script> dekho — wo sirf BankingFacade.getInstance() se baat karta hai.

14. Builder Creational
File: js/builder.js

Transaction request me bahut fields hain. Sab constructor me daalne ke bajaye builder step by step banata hai aur build() par check karta hai:

TransactionBuilder.create() .debit() .type("Transfer") .amount(5000) .via("transfer", "upi") // Bridge .to("SB123456") .remark("Rent") .build();

Live proof: Transfer page ka source dekho — bilkul yahi code hai.

Ek transaction me kya kya chalta hai

Jab aap "Send Money" dabate ho to ye order chalta hai:

  1. Builder — page request object banata hai
  2. Facade — request BankingFacade.transact() ko jaati hai
  3. Command — ek TransactionCommand banta hai aur invoker use chalata hai
  4. Singleton — config, database aur session ek hi jagah se milte hain
  5. Proxy — owner check hota hai aur access log hota hai
  6. Decorator — account ke add-ons padhe jaate hain (overdraft limit)
  7. Bridge (+ Adapter agar wallet hai) — gateway ki fee nikalti hai
  8. State — account Active hai ya nahi
  9. Chain of Responsibility — amount approval chain se guzarti hai
  10. Bridge — gateway payment process karta hai
  11. Proxy — balance update hota hai
  12. Observer — sabhi alerts jaate hain aur DB me row insert hoti hai
  13. Decorator — cashback aur reward points milte hain
Ye poora flow js/app.js ke executeTransaction() function me hai — viva me yahi function dikhana sabse acha rahega.
