Implementation of Singleton and Chain of Responsibility

Experiment 1
Aim: To implement the Singleton and Chain of Responsibility design patterns in a banking system, where shared services exist only once and every withdrawal is approved by a chain of officers.

1. Singleton Creational

Intent: Ensure a class has only one instance and provide a global point of access to it.

SmartBank me: BankConfig (bank ke rules), DatabaseConnection (ek hi DB connection), SessionManager (kaun login hai). CommandInvoker aur BankingFacade bhi singleton hain.

  • Constructor me check: if (BankConfig.instance) return BankConfig.instance;
  • new BankConfig() likhne par bhi purana object hi milta hai.
  • Fayda: config aur DB connection ki do copies kabhi nahi bantin, sab ek hi data dekhte hain.

2. Chain of Responsibility Behavioural

Intent: Pass a request along a chain of handlers; each handler either processes it or forwards it to the next, so the sender does not know who will handle it.

SmartBank me: har debit (withdrawal, transfer, bill) is chain se guzarta hai: Account Status → Fraud Check → Clerk (10K) → Manager (1L) → Branch Head (10L) → Rejected.

  • setNext() handler lautata hai, isliye chain ek line me banti hai: a.setNext(b).setNext(c).
  • Naya handler (Account Status) baad me joda — kisi purani class ko nahi chhuna pada.
  • Fraud Check aaj ka total spend bhi dekhta hai (daily limit per day, per transaction nahi).

Conclusion: Singleton guarantees one shared configuration, database connection and session for the whole website. Chain of Responsibility decouples the sender of a debit request from the officer who approves it, so approval rules can be added or reordered without changing existing classes.

Implementation of Factory Method and Proxy

Experiment 2
Aim: To implement the Factory Method pattern for creating different kinds of bank accounts, and the Proxy pattern for controlled, lazy and logged access to an account.

3. Factory Method Creational

Intent: Define an interface for creating an object, but let subclasses decide which class to instantiate.

SmartBank me: AccountFactory.openAccount() common kaam karta hai (validation, unique account number, DB save, opening entry); asli object createAccount() banata hai jo har factory override karti hai.

4. Proxy Structural

Intent: Provide a surrogate for another object to control access to it.

SmartBank me: koi bhi page RealAccountService ko seedha use nahi karta. AccountProxy teen kaam karta hai — protection (owner hai?), virtual (real object der se banta hai) aur logging (har koshish access_log table me).

Conclusion: Factory Method lets the system create Savings, Current and Fixed Deposit accounts without the client naming concrete classes, and each type brings its own rules. The Proxy adds security, lazy loading and auditing in front of the real account object without changing that object.

Implementation of Abstract Factory and Bridge

Experiment 3
Aim: To implement the Abstract Factory pattern for building a complete UI family per banking channel, and the Bridge pattern to separate payment types from payment gateways.

5. Abstract Factory Creational

Intent: Provide an interface for creating families of related objects without specifying their concrete classes.

SmartBank me: ATM, Mobile App aur Web Portal — har channel ki family = Theme + Layout + Wording. Header ka dropdown badalte hi poori website ka look badal jaata hai.

6. Bridge Structural

Intent: Decouple an abstraction from its implementation so that the two can vary independently.

SmartBank me: payment ka kaam (Transfer / Bill / Recharge) aur raasta (UPI / Card / Net Banking / QuickPay Wallet) alag hierarchies hain. Payment ke andar gateway ka reference hi bridge hai.

Neeche ki har cell ek asli combination hai (Rs. 1,000 + gateway fee). Kisi bhi cell par click karo:

Conclusion: Abstract Factory guarantees that a channel's theme, layout and wording always come from the same family. Bridge lets 3 payment types work with 4 gateways using 7 classes instead of 12, and a new gateway needs only one new class.

Implementation of Observer Pattern with Database Connectivity

Experiment 4
Aim: To implement the Observer pattern so that every balance change notifies SMS, Email, Push and Low-Balance observers, and a Database Logger observer stores the transaction in a real SQLite database.

7. Observer Behavioural

Intent: Define a one-to-many dependency so that when one object changes state, all its dependents are notified automatically.

SmartBank me: TransactionSubject apne observers ko update(event) bhejta hai. Customer Settings page se observers attach / detach karta hai (har user ki apni settings). Transfer me paane wale ke observers bhi chalte hain.

Database Connectivity

start.bat (ya python server.py) se website chalao to DatabaseConnection asli SQLite file data/smartbank.db se judta hai — 6 tables, foreign keys, indexes. Har INSERT / UPDATE server ki window me dikhta hai. Server ke bina file seedha kholo to browser storage driver chalta hai — baaki code ko farak nahi padta, kyunki dono drivers ek hi interface follow karte hain. Staff login me Database page par ER diagram, SQL console aur live query log hai.

Conclusion: The Observer pattern keeps the account logic independent of how customers are informed — alerts can be switched on or off at runtime without changing the subject. Combined with the Database Logger observer and the SQLite connection, every transaction is permanently stored and can be queried with SQL.

Extra patterns that complete the system

Beyond the syllabus

8. State Behavioural

Intent: Let an object change its behaviour when its internal state changes.

Account Active / Frozen / Closed. Staff Bank Console se freeze karta hai; Frozen me paisa aa sakta hai, ja nahi sakta; Close karne par balance ka payout record hota hai.

9. Strategy Behavioural

Intent: Define a family of algorithms, encapsulate each one, and make them interchangeable.

Savings → simple interest, FD → compound (quarterly), Current → none. My Accounts page par interest asli me credit hota hai.

10. Command Behavioural

Intent: Encapsulate a request as an object, so it can be logged, queued and undone.

Har transaction ek TransactionCommand hai. Customer "Undo Last Transaction" kar sakta hai; staff kisi bhi entry ko reverse kar sakta hai — judi hui cashback aur transfer-in entries bhi apne aap wapas hoti hain.

11. Decorator Structural

Intent: Attach additional responsibilities to an object dynamically.

Cashback, Overdraft, Insurance, Reward Points — account par wrapper ki tarah chadhte hain. Overdraft ko approval chain bhi dekhti hai; cashback asli me credit hota hai.

12. Adapter Structural

Intent: Convert the interface of a class into another interface that clients expect.

"QuickPay" third party wallet paise me kaam karta hai aur statusCode deta hai. WalletGatewayAdapter use PaymentGateway jaisa bana deta hai, isliye wo Bridge me UPI / Card jaisa hi lagta hai.

13. Facade Structural

Intent: Provide a unified, simple interface to a set of interfaces in a subsystem.

Har page sirf BankingFacade se baat karta hai — login, transact, undo, freeze, interest, statement.

14. Builder Creational

Intent: Separate the construction of a complex object from its representation.

Transaction request step by step banti hai; build() galat request ko wahin rok deta hai.

Ek transaction me saare patterns

Full flow

Jab customer "Send Money" dabata hai to BankingFacade.transact() → executeTransaction() ye order follow karta hai:

  1. Builder — page request object banata aur check karta hai
  2. Facade — request BankingFacade.transact() ko jaati hai
  3. Command — TransactionCommand banta hai, invoker chalata hai aur history rakhta hai
  4. Singleton — config, database aur session ek hi jagah se
  5. Proxy — owner check + access log
  6. Decorator — account ke add-ons padhe jaate hain (overdraft limit)
  7. Bridge + Adapter — gateway ki fee (wallet ho to adapter ke through)
  8. State — account Active hai ya Frozen / Closed
  9. Chain of Responsibility — Account Status → Fraud Check → Clerk / Manager / Branch Head
  10. Proxy — balance update
  11. Observer — SMS / Email / Push alerts + Database Logger SQLite me row likhta hai
  12. Paane wale ke account me Transfer In entry aur unke observers
  13. Decorator — cashback aur reward points
